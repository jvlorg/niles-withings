### Pre-implementation snapshot and sizing assumptions (superseded by measured cap above)
- Alpha.10 is published and installed on test Niles: logo sanitizer/package validation passed, installed SVG geometry matches, saved account restored and subscriptions ready. No Niles frontend patch was installed. Temporary outbound closed afterward, isolated network and health 200 verified.
- Measured Withings `plugin_storage`: 4 records, 718 bytes including keys and values. This is a snapshot, not a fixed future state size.
- Host storage allowance: 1,048,576 bytes per add-on. Reserve at least 65,536 additional bytes for runtime growth and storage overhead; initial illustrative diagnostic budget was 982,322 bytes (not the implemented cap). Reconcile the actual quota accounting and all storage owners before choosing the final fixed cap; never consume space required for identity, deduplication or recovery.
- Planning estimate: 256 bytes per compact record, including its share of key/format overhead. Four transitions/day × three records/transition plus 24 lifecycle/health records/day gives 1,080 records over 30 days, 276,480 bytes (270 KiB). Current state plus reserve plus this history totals 342,734 bytes. These are assumptions, not measured journal encoding sizes.
- The budget holds 3,837 such records (127/day across 30 days). A busy example of 20 transitions and 96 health records/day requires 1,198,080 log bytes and does not fit. Multiple mats and failures share the same budget. Thirty days is a target subject to the byte cap, not a guaranteed unlimited retention period.

### Record and privacy contract
- Capture receipt time, provider event time when valid, bounded mat reference, event type, processing stage, outcome/reason and a bounded correlation reference.
- Cover webhook receipt → accepted/rejected/duplicate/stale/blocked decision → publication attempt/result. Distinguish successful host publication from an automation's execution or device actuation.
- Record startup, account restoration, refresh/subscription failures and recovery; use bounded health summaries instead of recording each successful background poll.
- Aggregate repeated identical failures with first/last timestamps and counts. Rate-limit malformed/untrusted event floods; expose suppression counts without allowing untrusted strings or identities to grow the journal.
- Never persist credentials, tokens, capability URLs, raw webhook bodies or arbitrary provider/error payloads. Keep device references local and bounded; exported history contains sensitive bed-presence timing and must be user-controlled, not public.
- Enforce both age and serialized-byte limits. Expose actual oldest/newest retained records, used bytes, truncation and suppression counts. Do not claim 30-day coverage when capacity eviction removed earlier evidence.
- Diagnostic persistence is best-effort and must not block or alter core event delivery. Bound failures and retries; do not recursively log journal failures into the same journal. Expose gaps honestly. Preserve existing at-most-once publication behavior; this work is not an outbox redesign.

## Implemented candidate
- Shared account OAuth, encrypted refresh and subscription lifecycle remains in `runtime::Owner`; `runtime::devices::DeviceRegistry` owns independent account/device-scoped adapters.
- The actual component callback/startup/refresh control/timer uses automatic discovery. No user selection or device-ID input is needed. Each eligible mat gets a deterministic account/device host ID, not an inventory-order or display-name ID.
- Inventory validity and subscription readiness are separate gates. Failed discovery/storage/registration revokes delivery; healthy lifecycle alone cannot override invalid inventory. Removed devices become unavailable. Unchanged successful discovery retains fresh occupancy.
- Presence restoration is unknown and replayed events are silent. Setup emits no bed action. Revocation clears cached occupancy.
- Per-device host registration, publication and HTTP/storage imports are isolated in `component/src/host_adapter.rs`; fleet/legacy compatibility is in `component/src/automatic.rs`. Obsolete singleton sink and manual selection/switch UI are removed. Legacy neutral coordinator APIs remain for migration regression coverage, not the normal component path.
- Durable `host_devices` records all owned host IDs before registration, including retired IDs, so cold startup can revoke stale host availability even when credentials cannot restore. This registry is bounded to 128 historical host IDs and 64 KiB; capacity/storage failure blocks activation rather than silently losing ownership.

## Alpha.7 migration contract
A valid persisted `selection` remains the authority for the old `room/withings_sleep` alias, only for its exact authenticated account/device pair. That mat retains its host identity and the unchanged account/device-scoped presence key. Additional mats use deterministic IDs. A replacement account cannot inherit the alias or history. Selection bytes are preserved, not rewritten into new ownership. Corrupt selection blocks delivery rather than silently renaming the mat.

The component migration test constructs the legacy Owner selection/accept/event flow using the same storage, then starts the automatic Plugin and proves legacy identity, unknown restoration, duplicate suppression, a second independent mat and new-account isolation. This is synthetic in-memory process-recreation evidence, not live database durability.
